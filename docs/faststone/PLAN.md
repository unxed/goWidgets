# PLAN — воспроизведение FastStone Image Viewer 5.6

> План составлен моделью более мощной, чем обычно работает в этом репозитории. Он **обязателен к
> исполнению**, если только обстоятельства «на земле» не мешают (тогда — [PLAYBOOK §1](PLAYBOOK.md)).
> Где мы сейчас — в [STATUS.md](STATUS.md).

Автор плана не открывал код бэкендов и не видел дистрибутив эталона. Всё, что здесь сказано о
внутренностях `core/` и `backends/*`, — **гипотеза из README**, которую исполнитель проверяет чтением
кода в первой итерации, где это нужно. Расхождение — не повод паниковать, а повод пройти PLAYBOOK §1.

## 1. Границы

- Эталон — FastStone Image Viewer **5.6**. Видео — вне охвата. Версии новее 5.6 — вне охвата.
- Цель — максимально точный UX и набор возможностей; нативные контролы, где это возможно (disdoc).
- Что именно входит, определяет `spec/INVENTORY.md` (итерация A2). До неё — только A- и B-итерации.
- Не строим «wxWidgets целиком»: виджет попадает во фреймворк, только когда его требует текущая итерация (D4).

## 2. Как устроены итерации (RUP в малом)

- **A — Начало.** Добыть эталон, составить инвентарь. Кода почти нет.
- **B — Уточнение.** Снять главные архитектурные риски и получить «ходячий скелет»: окно → Canvas → картинка → зум/пан. Первый релиз для пользователей — B4.
- **C–F — Построение.** Режимы и функции по инвентарю. Детали C–F допишет ревизия B7, а не автор этого плана.
- **G–H — Передача.** Партия 2 бэкендов, полировка.
- Итерация = 1–3 диалога. Одна итерация → один-два небольших патча. Патч >~600 строк диффа или касается >3 бэкендов — режь.
- Карточка итерации: **Входы** (что запросить у пользователя до начала) · **Делаем** · **Не делаем** · **Готово, когда** · **Показать пользователям**.

## 3. Предварительные решения

Нормативны как план. При реализации оформляются ADR под ближайшим свободным номером в `docs/adr/`
со ссылкой на этот раздел. Имена типов ниже — **рабочие**: перед кодом сверь с `vocabulary.json`
(ADR-0011; лежит в репозитории vtui). Нет файла или имени — спроси пользователя.

**D1. Canvas — «тонкая поверхность».** Go сам рисует в `*image.RGBA`; бэкенд лишь показывает буфер и
пробрасывает ввод. Никаких drawing-API (cairo/QPainter/GDI/CoreGraphics) в бэкендах. Причины: ABI-поверхность
в 4 раза меньше (один «блит» вместо набора рисующих вызовов), рисование тестируется в headless без GUI.
Отвергнуто: рисовать нативными API в каждом бэкенде.

Эскиз (не контракт):

```go
cv, err := win.AddCanvas()
cv.Paint.On(app.Scope(), func(f goWidgets.Frame) {
	// f.Image — *image.RGBA размером Size×Scale физических пикселей; рисуем в него целиком.
})
cv.Invalidate() // запросить перерисовку через планировщик Core; несколько вызовов за кадр схлопываются
// сигналы: MouseDown, MouseUp, MouseMoved, MouseWheel, DoubleClicked; MouseInfo{X, Y (DIP), Button, Mods, Delta}
// свойство Scale — физических пикселей на DIP; клавиатура — существующим KeyPressed; Focus() как у других виджетов
```

Семантика: каждый Paint получает полный буфер (частичная инвалидация — потом, если измерения потребуют);
во время перетаскивания мышь захвачена (Win32 `SetCapture`, у остальных — штатный grab); перестановка
каналов RGBA→BGRA/ARGB — один общий хелпер в `core`, не по копии на бэкенд; трогать Canvas можно только из UI-потока.

**D2. Изображения — в чистом Go.** stdlib `image/*` + `golang.org/x/image` (`draw`, `bmp`, `tiff`, `webp`).
Масштабирование: пока пользователь двигает/крутит — быстрое (NearestNeighbor/ApproxBiLinear); в покое —
качественное (CatmullRom) в фоновой горутине, результат через `app.QueueUpdate`, устаревшие задачи
отменяются (счётчик поколений или `context`). Математика вьюпорта (зум/пан/вписывание) — отдельный
чистый пакет с табличными тестами. Новые зависимости — только с разрешения (BACKLOG Q4).

**D3. Сетка миниатюр — на Canvas.** Нативного контрола с нужным поведением (размеры, подписи, рамки,
выделение, виртуализация одинаково на четырёх платформах) нет. Это отклонение от «нативность по
максимуму» фиксируется ADR и ждёт подтверждения (BACKLOG Q2).

**D4. Остальной UI — нативные контролы; виджеты — по требованию.** Меню/тулбар/статусбар/дерево/сплиттер
и т. д. добавляются в фреймворк в той итерации, которой они нужны, и не раньше. Уже есть `MenuItem`
и `Separator` (трей) — переиспользуй, не изобретай второй тип.

**D5. Текст на Canvas** (подписи миниатюр, OSD): растеризация в Go (`golang.org/x/image/font/opentype`
и встроенные Go-шрифты; **проверить покрытие кириллицы**) либо нативный виджет поверх. Решение — отдельным
спайком в C3, не раньше.

**D6. Партии бэкендов.** Партия 1 = headless + gtk + win32 (реализуется в итерации виджета).
Партия 2 = qt (6 и 5) + cocoa (отдельные итерации G). Пока партии 2 нет, виджет в этих бэкендах —
«возможности нет» (как у трея без статусной области), а не паника; отмечается в матрице §6.

**D7. Приложение** — `showcase/fsv` (рабочее имя, BACKLOG Q3). Настройки — JSON в `os.UserConfigDir()`;
переменные окружения только для отладки. Сомнение между двумя поведениями → настройка, а не спор.

**D8. HiDPI.** Геометрия в DIP, буфер Canvas — в физических пикселях, `Scale` — свойство. Тесты — при Scale 1 и 2.

## 4. Порядок работы внутри итерации виджета

1. Ближайший аналог (ListBox/ComboBox) — **скопируй его путь** через все слои: публичный API → core → headless → gtk → win32. Не изобретай структуру.
2. Сначала headless и его тест, потом gtk (Xvfb), потом win32 (Wine, `win32test`).
3. Ввод в GUI-тестах — настоящими нажатиями (xdotool под Xvfb), как в существующих тестах.
4. Каждый слой — отдельный небольшой патч, если суммарно больше лимита из §2.

### A1 — получить и прочитать эталон (без кода)

- **Входы:** доступ из песочницы к `2g0.ru` либо файл от пользователя.
- **Делаем:** [REFERENCE.md](REFERENCE.md) §2–§5 строго по порядку. Результат — `spec/REFERENCE-NOTES.md`: URL, размер, sha256, тип инсталлятора, чем извлекли, формат help, путь к оглавлению, кодировка.
- **Не делаем:** не читаем help целиком; не ищем другие источники бинаря без разрешения; ничего не коммитим из эталона (Q1).
- **Готово, когда:** файл заполнен, либо задан вопрос по сценарию из REFERENCE §3–§4.

### A2 — инвентарь из help (без кода)

- **Входы:** результат A1.
- **Делаем:** оглавление help → `spec/INVENTORY.md` по формату REFERENCE §7. Одна секция help за ответ; вопросы «in/later/out?» — пачкой ≤5 в конце ответа.
- **Не делаем:** не реализуем; не решаем сами, что «out» (кроме видео); не пересказываем help — только ID, заголовок, суть в одну строку своими словами.
- **Готово, когда:** покрыты все верхнеуровневые разделы help; спорное помечено `?`.

### A3 — CI-эталон

- **Входы:** A1 показал, что установщик работает под Wine (иначе вопрос пользователю).
- **Делаем:** `.github/workflows/fsref.yml` (только `workflow_dispatch`) + `tools/fsref/`: скачать установщик, сверить sha256, поставить тихо под Wine, запустить в Xvfb, сценарии xdotool → скриншоты → `upload-artifact`. Сценарии перечислены в `spec/SCENARIOS.md` (ID сценария ↔ имя скриншота ↔ ID из инвентаря). Стартовый набор: браузер по умолчанию, просмотр картинки, полноэкранный режим с мышью у каждого края, по одному диалогу на каждую группу меню.
- **Не делаем:** не пытаемся автоматизировать всё; не коммитим скриншоты (Q1, Q7); тестовые картинки генерируем кодом, не берём чужие.
- **Готово, когда:** пользователь запустил workflow и получил артефакт хотя бы с тремя сценариями. Не запускается под Wine после одного раунда бисекции → вопрос пользователю.
- **Замечание:** модель не может скачать артефакты Actions (обычно нужен вход) — скриншоты прикладывает пользователь.

### B1 — Canvas: core + headless

- **Входы (запроси разом):** вывод `tree -L 2 core backends showcase docs`; все файлы, где реализован `ListBox` во всех слоях (`grep -rl ListBox --include=*.go .`); разделы `docs/disdoc.md` про виджеты, события и конвейер кадра; ADR-0011 и записи `vocabulary.json` про поверхность рисования; образец headless-теста.
- **Делаем:** публичный тип Canvas; узел в core; сигналы ввода; `Invalidate` → Paint через планировщик; буфер в физических пикселях (D8); хелпер перестановки каналов; headless-бэкенд создаёт буфер и позволяет тесту «нажать мышью»; ADR по D1 и D8.
- **Тесты:** Paint вызывается с буфером верного размера при Scale 1 и 2; несколько `Invalidate` за кадр → один Paint; события мыши приходят с DIP-координатами; отписки не текут (по образцу теста на утечки подписок); хелпер каналов — табличный тест.
- **Не делаем:** реальные бэкенды, текст, курсоры, частичную инвалидацию.
- **Готово, когда:** тесты зелёные в CI пользователя; ADR; матрица §6; STATUS.

### B2 — Canvas: GTK

- **Гипотеза для проверки чтением кода бэкенда:** `GtkDrawingArea`, буфер через `cairo_image_surface_create_for_data` и отрисовка в сигнале `draw`; события через `gtk_widget_add_events` и сигналы button-press/motion/scroll. Кэшируй cairo-поверхность, не пересоздавай на каждый кадр.
- **Тесты (Xvfb):** нарисованный узор → скриншот корня → сравнение пикселей в контрольных точках; клики и колесо через xdotool доходят сигналами с верными координатами; Scale=1.
- **Готово, когда:** тесты в CI зелёные; матрица; STATUS.

### B3 — Canvas: Win32

- **Гипотеза:** собственный класс окна, `WM_PAINT` + `SetDIBitsToDevice`/`StretchDIBits` с top-down DIB (отрицательная высота), `SetCapture` при перетаскивании, `WM_MOUSEWHEEL`.
- **Тесты:** `backends/win32/win32test` под Wine по образцу существующих.
- **Готово, когда:** как B2. Помни: Wine ≠ Windows (R5).

### B4 — `showcase/fsv` v0.1

- **Делаем:** окно + Canvas; открыть файл (`win.OpenFile` с фильтрами); декодировать jpeg/png/gif/bmp (stdlib и `x/image`); показать «вписать в окно»; Ctrl+O, Esc; CI собирает бинарники windows/linux по образцу `showcase/crescent` (если для него есть job — повтори); раздел «как запустить» в README приложения.
- **Не делаем:** зум, пан, соседние файлы, меню (B6 и далее).
- **Показать пользователям:** бинарь на настоящем Windows и на Linux. Вернувшуюся обратную связь занеси в BACKLOG.

### B5 — спайк: Canvas на Qt (ограничен по времени)

- **Вопрос:** можно ли на Qt 6 и Qt 5 без CGO показать RGBA-буфер и получить события мыши/колеса?
- **Кандидаты по порядку:** (a) тот же механизм перехвата событий, который бэкенд уже использует для других виджетов (ADR-0013), на потомке `QWidget`; (b) показ буфера через `QLabel` + `QPixmap::fromImage(QImage(...))`.
- **Результат:** ADR «Canvas на Qt: да / нет / как», минимальный работающий пример под Xvfb, без полной интеграции. Нет ответа за один диалог → вопрос пользователю. **D1 самостоятельно не пересматривать.**

### B6 — просмотр: зум, пан, соседние файлы

- **Делаем:** режимы «вписать / 1:1 / заполнить»; зум колесом относительно курсора; пан перетаскиванием с захватом мыши; ←/→, PgUp/PgDn, Home/End по файлам каталога (естественная сортировка по имени); D2 (быстро при движении, качественно в покое, отмена устаревшего).
- **Тесты:** математика вьюпорта — отдельный чистый пакет (`showcase/fsv/viewport`) с табличными тестами без GUI; порядок файлов — тест; отмена устаревших задач — тест на счётчик поколений.
- **Показать пользователям:** новая сборка.

### B7 — ревизия плана (без кода)

- **Делаем:** по итогам инвентаря (A2) и B4–B6 переписать §5 «Контур C–H» в полноценные карточки; приоритеты — вместе с пользователем (вопросы пачкой ≤5). Подчистить BACKLOG.

### Контур C–H (черновик; уточняется в B7)

- **C — Браузер:** C1 меню + статусбар (+ тулбар); C2 сплиттер + дерево папок (ленивая загрузка); C3 сетка миниатюр на Canvas (спайк текста D5; фоновые воркеры + `QueueUpdate`; отмена при смене папки); C4 раскладка «дерево | сетка | предпросмотр»; C5 выделение, сортировка, фильтры, контекстное меню.
- **D — Полноэкранный просмотр:** полноэкранный режим окна; панели, выезжающие у краёв экрана (точное поведение — по скриншотам эталона, не по памяти); скрытие курсора.
- **E — Правка:** диалоги (поворот, кадрирование, размер, цвет, …) — понадобятся Slider, SpinEdit, RadioButton, GroupBox; набор по инвентарю.
- **F — Прочее из инвентаря:** слайд-шоу, сравнение, пакетные операции (нужен ProgressBar) и т. д.
- **G — Партия 2:** qt (6, 5) и cocoa для всех использованных виджетов; вопрос Q5 про macOS-раннер.
- **H — Полировка:** производительность (измерять, не гадать), настройки, локализация.
