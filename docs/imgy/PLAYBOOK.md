# PLAYBOOK — как себя вести

Правила для модели-исполнителя и для человека, который её ведёт. Они закреплены пользователем и
действуют в каждом диалоге. Если правило и инструкция в чате противоречат друг другу — приоритет у чата;
отметь расхождение одной строкой.

## 0. Главное за десять строк

1. Нет данных → **остановись и спроси**. Не гадай, не делай «хоть как-то». Fail fast.
2. Сначала патч; Windows можно проверять локально. Linux/macOS и недоступные локально конфигурации проверяй в GitHub CI; для визуальных изменений сохраняй screenshot-артефакты. Не подменяй CI непроверенной сборкой.
3. Патч — только дельта. Не повторяй содержание предыдущих патчей.
4. Каждый ответ: патч + тесты нового кода + правки документации (минимум `STATUS.md`).
5. Отладка — бисекция, не микрошаги (§6).
6. Строго в рамках задачи итерации. Постороннее — одна строка в `BACKLOG.md` и назад к задаче (§7).
7. Сомнение между двумя поведениями → настройка, а не гадание.
8. Перед каждым вызовом инструмента, начиная с десятого, — пять вопросов (§5).
9. Два ответа подряд без конкретного результата недопустимы. Один ответ «просто подумать» — нормально.
10. Сообщение пользователя из одной правой скобки `)` = «хорошо, продолжай»: делай следующий шаг плана.

## 1. Отклонение от плана

План обязателен. Отклоняться можно, только когда «на земле» иначе, чем предполагает план.

1. Зафиксируй расхождение **доказательством** (цитата кода, вывод команды, фрагмент лога), а не мнением.
2. Входит ли оно в свободу исполнителя? Да, если это: имена приватных функций и файлов внутри пакета, структура тестов, порядок подшагов внутри итерации, мелкая правка того, что итерация и так трогает. Тогда действуй и отметь одной строкой в `STATUS.md`.
3. Иначе (меняется публичный API, состав итераций, решение D1–D8, набор зависимостей, поведение относительно эталона): опиши не более двух альтернатив (по строке плюсов/минусов), дай рекомендацию и задай вопрос пользователю. До ответа не реализуй.
4. После ответа: архитектурное — ADR (ближайший свободный номер в `docs/adr/`), остальное — строка в `PLAN.md` с пометкой «изменено:».

«Так никто раньше не делал» — не аргумент против решения. Красивое и простое решение лучше сложного: ищи его.

## 2. Формат ответа

1. Если это отладка: три строки — **что узнали / чего не знаем / как узнать**.
2. Патч (§3).
3. Как проверить: команды для пользователя.
4. Что показать пользователям (из карточки итерации).
5. Вопросы: не более 5, пронумерованные, у каждого — умолчание, с которым работаем без ответа, и способ получить данные (команда для копирования).

## 3. Патч

- Формат: `git format-patch`, применимый через `git am`. Сообщение коммита **на английском**, с `Refs: docs/imgy/PLAN.md (<ID итерации>)`.
- **База — текущий код пользователя** (дамп, который он прислал), а не upstream HEAD. Нет дампа нужных файлов → запроси, не восстанавливай по памяти.
- Как собрать патч, если есть песочница: разложи в пустой git-репозиторий **только те файлы, которые меняешь**, байт-в-байт из дампа; закоммить как базу; внеси правки; `git format-patch`. Новые файлы — целиком, изменённые — дельта.
- Не прогоняй `gofmt`/рефакторинг по чужим файлам; форматируй только свои строки. Не меняй окончания строк.
- **Не пиши в `filelist.md`** — его ведёт другой процесс.
- Если пользователь просит другой формат (например, AP-патч с якорями) — следуй описанию из его сообщения.
- Сначала отдай патч. Потом спроси разрешения гонять сборку/тесты у себя.
- Новый код без теста не отдаётся. Если тестовых файлов нет в запросе и нет интернета — запроси их.
- Логи, которые добавляешь для отладки: компактные (одна строка на событие, счётчики вместо потока, кольцевой буфер ~200 строк, дамп по ошибке), включаются переменной окружения по образцу существующих. Цель — чтобы пользователь мог прислать хвост ≤50 строк, не сжигая чужие токены.

## 4. Fail fast: что делать при сбое

| Ситуация | Действие |
|---|---|
| Не удалось скачать/прочитать файл, страницу, тикет, дамп | СТОП. Напиши: что пробовал (команда + вывод ≤10 строк), что нужно, как пользователь может это дать |
| Нет нужного файла (код, тест, `vocabulary.json`, ADR) | СТОП. Точный список путей и команда, которой пользователь их скопирует |
| Нет интернета, а он нужен | СТОП. Попроси файл; альтернативные источники сам не ищи |
| Сборка/тест упали (в разрешённом прогоне) | Один прогон — один вывод. Хвост лога ≤50 строк → §6. Не перезапускай вслепую |
| Среда сломалась / кончились лимиты | СТОП, отчёт, вопрос. Среду самодельными средствами не чини |
| Кэш сборки Go | **Никогда** `rm -rf /root/.cache/go-build` между сборками. Чистить кэш только по конкретному диагнозу (доказанная порча) |
| Help и реальный эталон расходятся / help молчит | Пометь `?` в инвентаре, вопрос в пачку. Реализовывать «по догадке» нельзя (REFERENCE §7) |
| Не хватает места в ответе | Отдай завершённую атомарную часть; остальное — в `STATUS.md` «Следующий шаг» |
| Тесту нужен GUI, которого нет | Headless-часть протестируй; GUI-часть — команда для пользователя/CI |
| Не уверен, входит ли что-то в задачу | Не входит. Строка в BACKLOG, назад к задаче |

Правило по умолчанию: остановка и вопрос дешевле двадцати вызовов инструментов.

## 5. Лимиты инструментов

Ответы, которые «вылетают» за лимит вызовов, — почти всегда признак того, что ты зарылся не туда.
**Перед каждым вызовом инструмента, начиная с десятого, ответь себе:**

1. Не слишком ли глубоко я зарылся?
2. Не ушёл ли я с головой в «любимую» гипотезу, игнорируя остальные?
3. Не занимаюсь ли я оверинженирингом? Не overcomplicated ли то, что делаю?
4. Следую ли я fail fast?
5. Точно ли настолько сложное решение — единственное? Нет ли способа проще и изящнее?

Хоть один ответ «да / не знаю» → остановись, отдай то, что есть, и задай вопрос.

## 6. Отладка

Метод — **бисекция**: каждый ход отсекает ~50% подозреваемой поверхности, проверяется экспериментом, повторяется.
Не микрошаги (убрать одну мелочь и посмотреть). Не аналитическое перебирание гипотез по одной — на этом проекте оно
эмпирически даёт ноль и сжигает бюджет. Не уходи в тангенты без явного разрешения.

Алгоритм на каждом шаге: 1) что узнали на предыдущем шаге; 2) чего ещё не знаем; 3) как это узнать.

Если тупик — **дифференциальный диагноз**:
1. Выпиши все симптомы.
2. Выпиши все возможные диагнозы.
3. Вычеркни диагнозы, противоречащие хотя бы одному симптому.
4. Следующий эксперимент — тот, что отсекает половину оставшихся.

Стартовые разрезы для этого проекта:

| Симптом | Первая бисекция |
|---|---|
| Что-то не так на одном бэкенде | Тот же сценарий в headless: ок → проблема в бэкенде; не ок → в core. Дальше внутри бэкенда: вызов платформы / преобразование данных / порядок событий |
| Чёрный или пустой Canvas | Сравни буфер, который получил бэкенд (контрольная сумма/пиксель в логе), с тем, что нарисовал Go: совпал → проблема показа; нет → проблема рисования |
| Падение при старте | Отдельно: инициализация бэкенда / создание окна / первый кадр. Диагностика: `app.Diagnostics()` |
| Вёрстка «поехала» | Голден-тест layout в headless: тот же набор констрейнтов; затем убери половину правил; смотри `LayoutConflicts` |
| Зависание/гонка | Все ли обращения к виджетам идут из UI-потока? Фоновая работа — только через `app.QueueUpdate` |

Нужны данные, которых нет, — не гадай: дай пользователю патч, собирающий компактный лог, или команду, которая его получит.

## 7. Границы задачи (перфекционизм запрещён)

- Работаем строго в рамках итерации. Никакого рефакторинга и «улучшения смежного кода» по пути.
- Наткнулся на ошибку или принял неоднозначное решение: **одна строка** в `BACKLOG.md` §2 (и, если нужно, комментарий в коде рядом), в ответе — одна строка о находке, и сразу возвращайся к задаче. Чинить — только по разрешению; по умолчанию — в конец очереди.
- Цель — как можно быстрее дать пользователям что-то юзабельное для проверки.
- Решение, в котором есть сомнение (порог, умолчание, поведение), можно вынести в настройку (D7): не пренебрегай этим.
- Работай небольшими атомарными частями: так проще рассчитывать лимиты.

## 8. Технические ограничения проекта

- **Без CGO.** Windows — `golang.org/x/sys/windows` и `syscall.NewCallback`; Linux — `purego` (подменён `pureffi` директивой `replace`); Qt — по манглированным символам (ADR-0013); Cocoa — рантайм Objective-C (ADR-0014).
- Зависимости: только `backends/* → core`, никогда наоборот. Драйверы регистрируются в `init()`.
- Имена виджетов, свойств, сигналов — по словарю vtui (`vocabulary.json`, ADR-0011). Нет имени — спроси.
- Из фоновой горутины виджеты трогать нельзя — только `app.QueueUpdate`. На macOS `NewApp` вызывается из `main`.
- Debug-сборка: `-tags goWidgets_debug` должна проходить тесты.
- Новый виджет: найди ближайший существующий и повтори его путь по слоям (PLAN §4). Тесты — по образцам: headless, голден-layout, `backends/qt/qttest`, `backends/win32/win32test`.
- Отклонения от `docs/disdoc.md` — только через ADR.
