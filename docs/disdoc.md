

# goWidgets


Этот дизайн-документ (Design Document) составлен специально как исчерпывающее техническое задание. Он структурирован так, чтобы даже базовая LLM без доступа к интернету могла шаг за шагом реализовывать архитектуру, не сбиваясь с курса.

Документ строго следует **итеративной методологии RUP (Rational Unified Process)**: мы не пишем весь фреймворк целиком, а развиваем его через вертикальные срезы (от Inception до Transition).

# Design Document: `vgui` (Cross-Platform Go Native UI)

## 1. Концепция и Позиционирование
**`vgui`** — это кроссплатформенная GUI-библиотека для Go.
**Главная цель:** дать Go-разработчикам инструмент для создания десктопных приложений без боли с `CGO` и зависимостями, сохраняя при этом нативный опыт на ключевых платформах.

### 1.1. Базовые принципы (Строгие правила для ИИ)
1. **Никакого `CGO` (`CGO_ENABLED=0`).** Это абсолютное правило. Весь FFI реализуется через `syscall` (Windows) или `purego` (macOS, Linux/GTK). Библиотека `qt.go` **исключается** из проекта, так как она генерирует C++ шимы и требует CGO.
2. **Публичный API скрывает платформу.** Пользователь работает с `vgui.Button`, а не с `vgui.Win32Button`.
3. **Единый Layout-движок.** Платформенные менеджеры компоновки (Sizers в GTK, AutoLayout в Cocoa) **не используются**. Ядро `vgui` само считает координаты через собственный движок (на базе констрейнтов / Cassowary) и передает бэкенду готовые абсолютные координаты `(X, Y, Width, Height)`.
4. **Итеративность (Showcase-driven).** Мы пишем только те виджеты и функции, которые нужны для работы целевого приложения-демонстратора (клона FastStone Image Viewer).

## 2. Архитектура (Уровни системы)

Система делится на 3 строгих слоя. LLM не должна допускать протекания абстракций между ними.

### Уровень 1: Frontend (Public API)
Декларативный/компонентный интерфейс, вдохновленный `vtui` (стараемся держать API настолько близким к vtui, насколько возможно —
разработчикам, писавшим под vtui, должно быть легко адаптироваться). Ничего не знает о `purego` или `syscall`.
https://github.com/unxed/vtui
* **Сущности:** `App`, `Window`, абстрактные виджеты (`Button`, `Label`, `TextInput`, `TreeView`, `Canvas`).
* **Layout:** Пользователь задает правила (констрейнты, Cassowary, аналоги якорей `vtui`).
* **События:** Обработчики `OnClick`, `OnResize`, `OnKeyPress`.

### Уровень 2: Core (Диспетчер и Вычислитель)
Скрыт от пользователя. Связывает Frontend и Backend.
* **Layout Solver:** Реализация алгоритма Cassowary. При ресайзе окна решает систему уравнений, получает плоские пиксельные координаты.
UPD: Реализация алгоритма Cassowary уже готова в отдельной библиотеке, берём оттуда: https://github.com/unxed/kiwi-go
* **Event Router:** Транслирует платформенные события (например, `WM_LBUTTONDOWN` из Win32) в абстрактные (`vgui.MouseClick`).
* **App Context:** Управляет Event Loop (главным циклом), следит, чтобы обновления UI происходили в Main Thread.

### Уровень 3: Backends (Драйверы платформ)
Слой реализации `PlatformDriver`. Каждая кнопка или окно в Frontend имеет своего двойника в Backend.
* **Ebiten / Custom Renderer:** Отрисовка с нуля. Используется как fallback и для проверки API на ранних этапах.
* **GTK Driver (`puregotk`):** Для Linux. Динамически грузит `libgtk-3.so` в рантайме.
* **Win32 Driver (`syscall`):** Для Windows. Создает нативные HWND контролы (`BUTTON`, `EDIT`).
* **Cocoa Driver (`purego`):** Для macOS. Взаимодействует с `libobjc.dylib` через отправку сообщений (msgSend).

## 3. Интерфейсы ядра (Contract API для LLM)

ИИ должен опираться на эти интерфейсы при проектировании слоев.

```go
// --- PUBLIC API (Уровень 1) ---

type Widget interface {
    SetID(id string)
    ID() string
    // Установка констрейнтов для Cassowary solver'а
    SetConstraints(c ...Constraint)
}

type Window interface {
    Widget
    SetTitle(title string)
    SetContent(w Widget)
    Show()
}

type App interface {
    Run(mainWindow Window) error
    QueueUpdate(f func()) // Безопасное обновление UI из горутин
}


// --- BACKEND API (Уровень 3 - Скрыто от пользователя) ---

// PlatformDriver инициализирует нужную ОС
type PlatformDriver interface {
    Init() error
    RunMainLoop() error
    CreateWindow(title string, width, height int) (BackendWindow, error)
}

type BackendWindow interface {
    SetTitle(title string)
    Show()
    // Метод, через который Core передает готовые координаты
    UpdateLayout(rects map[string]Rect) 
}

type Rect struct { X, Y, W, H int }

// BackendWidget — обертка над HWND, GtkWidget* или NSView*
type BackendWidget interface {
    SetBounds(r Rect)
    SetVisible(v bool)
}
```

## 4. План реализации: Итерации RUP

Работу с LLM нужно выстраивать **строго по этим фазам**. Запрещается переходить к следующей итерации, пока не закрыта текущая.

### Фаза 1: Inception (Проверка концепции)
**Цель:** Доказать жизнеспособность связки "Абстрактный API -> Драйвер".
* **Задача 1:** Создать скелет проекта (`core`, `vgui`, `backends/ebiten`).
* **Задача 2:** Реализовать `Ebiten` драйвер (самый простой, так как не требует сложного FFI).
* **Задача 3:** Написать 1 виджет: `vgui.Button`.
* **Задача 4:** Написать ручной (заглушечный) расчет координат без Cassowary.
* **Результат:** Приложение "Hello World", открывающее окно Ebiten с одной кнопкой `[Кликни меня]`, реагирующей на мышь.

### Фаза 2: Elaboration 1 (FFI и Абстракция)
**Цель:** Доказать, что абстракция выдержит нативный тулкит.
* **Задача 1:** Добавить `backends/gtk` с использованием `puregotk`.
* **Задача 2:** Настроить автоматический выбор: запускаем на Linux — пытаемся загрузить GTK, если `libgtk-3.so` нет — падаем (диалог установки прикрутим позже).
* **Задача 3:** Реализовать ту же кнопку `vgui.Button` через `puregotk`.
* **Результат:** Тот же самый `main.go` из Фазы 1 компилируется и работает через GTK. Код публичного API не изменился.

### Фаза 3: Elaboration 2 (Движок Layout и Констрейнты)
**Цель:** Решить фундаментальную проблему разметки.
* **Задача 1:** Интегрировать алгоритм Cassowary (например, портировать готовый решатель на Go или написать простую обертку).
* **Задача 2:** Реализовать публичные абстракции: `VBox`, `HBox` и `Anchor` (которые под капотом транслируются в линейные уравнения Cassowary).
* **Задача 3:** Изменить логику бэкендов: теперь при `OnResize` Core-слой решает констрейнты и рассылает всем `BackendWidget` команду `SetBounds(x, y, w, h)`. GTK-бэкенд использует `GtkFixed`, чтобы позиционировать контролы абсолютно.
* **Результат:** Окно с 3 кнопками, которые корректно меняют размер при растягивании окна (через Ebiten и GTK).

### Фаза 4: Construction 1 (Windows MVP)
**Цель:** Нативный опыт на Windows.
* **Задача 1:** Написать `backends/win32` (используя пакет `golang.org/x/sys/windows`).
* **Задача 2:** Регистрация `WNDCLASSEX`, цикл `GetMessage`, `DispatchMessage`.
* **Задача 3:** Обернуть системные классы `BUTTON`, реагировать на `WM_COMMAND`. Интегрировать команду `MoveWindow` для работы Layout-движка.
* **Результат:** Приложение работает нативно на Windows (CGO_ENABLED=0).

### Фаза 5: Construction 2 (Базовые элементы для Showcase)
**Цель:** Набор виджетов для диалога настроек и базового UI FastStone.
* **Задача 1:** Добавить виджеты: `Label`, `TextInput`, `CheckBox`, `Splitter` (сплиттер должен генерировать новые констрейнты для Cassowary при перетаскивании).
* **Задача 2:** Реализовать их для GTK, Win32 и Ebiten.
* **Результат:** Полноценный "Окно настроек" с чекбоксами и полями ввода, работающий на 3 бэкендах.

### Фаза 6: Construction 3 (Тяжелые виджеты)
**Цель:** Сделать ядро FastStone (Дерево, Грид, Канвас).
* **Задача 1:** `TreeView` (Win32: `SysTreeView32`, GTK: `GtkTreeView`).
* **Задача 2:** `GridView` / `IconView` (для отображения миниатюр картинок).
* **Задача 3:** `Canvas` — виджет для прямой отрисовки пикселей/картинок.
    * Win32: `BitBlt` / GDI+.
    * GTK: `cairo_paint` на `GtkDrawingArea`.
* **Результат:** Готовый UI-каркас: слева дерево каталогов, справа иконки, внизу превью.

### Фаза 7: Construction 4 (macOS Cocoa)
**Цель:** Закрыть третью главную платформу.
* **Задача 1:** Написать `backends/cocoa` через `purego` и `objc_msgSend`.
* **Задача 2:** Инициализация `NSApplication`, `NSWindow`, `NSButton`.
* **Задача 3:** Как и в GTK, выключить AutoLayout (`setTranslatesAutoresizingMaskIntoConstraints:NO`) и двигать контролы абсолютно через `setFrame:`.
* **Результат:** Проект полностью кроссплатформенный (Win, Mac, Lin) на чистом Go.

### Фаза 8: Transition (Полировка Showcase и Fallback)
**Цель:** Релиз-кандидат.
* **Задача 1:** Сборка showcase-приложения (клон FastStone Lite). Полноценная работа с файловой системой через `Canvas` и `TreeView`.
* **Задача 2:** Реализация механизма "Авто-fallback на Linux" (Если `puregotk` вернул ошибку -> диалог терминала "Скачать GTK?" -> если отмена -> запуск Ebiten-бэкенда).
* **Задача 3 (Дополнительная, из concept):** Исследование хинтинга текста в Ebiten бэкенде (эвристики FreeType или байткод TrueType) для идеального рендеринга fallback-интерфейса.

## 5. Инструкции по промптингу для слабых моделей

Когда вы будете давать задачи модели без доступа к сети, используйте следующий формат:

1. **Контекст фазы:** "Мы сейчас находимся в *Фазе 4: Construction 1*. Наш фокус — только Windows Win32 API. Не используй CGO. Используй `golang.org/x/sys/windows`."
2. **Изоляция:** "Не пытайся сейчас реализовать macOS или GTK. Твоя задача реализовать только файл `backend_windows.go` интерфейса `PlatformDriver`."
3. **Ограничение скоупа:** "Не пиши сразу всю систему окон. Напиши только функцию `RegisterClassEx` и `CreateWindowEx` для главного окна."
4. **Контроль архитектуры:** "Помни про Cassowary. Win32-код не должен сам вычислять размеры. Он должен только принимать структуру `Rect` и вызывать `MoveWindow`."

## 6. Риски и их локализация (Для ИИ)

* **Риск:** LLM начнет придумывать свои типы событий для каждой ОС.
* **Решение:** Жестко задать единый `Event` struct в Core-пакете. Бэкенды обязаны мапить нативные события (например `NSEventTypeLeftMouseDown` на Mac) в этот единый struct перед передачей во Frontend.
* **Риск:** Ebiten (игровой движок) сожрет батарею на перерисовках.
* **Решение:** Ebiten бэкенд должен использовать `ebiten.SetRunGameMode(ebiten.RunGameModeEventDriven)` (отрисовка только при наступлении событий, а не 60 FPS).
* **Риск:** Objective-C runtime слишком сложен для LLM.
* **Решение (для Фазы 7):** Разбить фазу 7 на микро-шаги. Сначала написать хелперы `msgSend` для строк, потом для классов, потом только создавать `NSWindow`.
