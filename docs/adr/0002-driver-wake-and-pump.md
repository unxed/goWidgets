# ADR-0002. `PlatformDriver` получает `Wake()`, а `RunMainLoop` — колбэк `pump`

* Статус: принято
* Дата: 2026-09-08
* Затрагивает: §4.4 «Backend API», §4.5 «Потоковая модель»

## Контекст

§4.5.3 требует, чтобы горутины взаимодействовали с UI через `App.QueueUpdate`.
§4.4 описывает драйвер с `RunMainLoop(ctx)` и без каких-либо средств разбудить его.

Это неисполнимо. Нативный цикл блокируется внутри `GetMessage` (Win32) или
`gtk_main` (GTK) и не вернёт управление до прихода события. Положить функцию в
очередь из фоновой горутины можно, но выполнить её будет некому и некогда: поток,
которому принадлежит UI, спит в системном вызове. Ждать «какого-нибудь» события
нельзя — на простаивающем приложении его может не быть часами.

## Решение

Контракт расширен двумя точками:

```go
RunMainLoop(ctx context.Context, pump func()) error
Wake()
```

* `Wake` безопасен из любой горутины и обязан прервать блокировку цикла.
* `RunMainLoop` вызывает `pump` один раз до входа в цикл и затем после каждого
  `Wake`. `pump` — это `core.App.DrainQueue`, то есть работа исполняется на том
  самом потоке, который владеет виджетами.

Реализации: Win32 — `PostMessageW` в message-only окно с `WM_APP+1`;
GTK — `g_idle_add`, один из немногих документированно потокобезопасных вызовов GLib;
headless — буферизованный канал.

## Последствия

* `QueueUpdate` становится исполнимым, а не декларативным.
* Каждый новый драйвер обязан реализовать `Wake`; для Cocoa это
  `performSelectorOnMainThread:`, для web — микротаск.
* Отмена `ctx` тоже идёт через эту дверь: горутина ждёт `ctx.Done()` и просит
  UI-поток завершиться сам (`PostQuitMessage` и `gtk_main_quit` можно звать
  только со своего потока).

## Альтернативы

* Опрос очереди по таймеру — отвергнуто: ломает NFR «простой UI = 0% CPU».
* Глобальная функция в `core`, которую драйвер зовёт напрямую — отвергнуто:
  прячет зависимость и мешает нескольким `App` в тестах.
