# ADR-0008. Фокус, порядок Tab, и проверка Win32 под Wine

* Статус: принято
* Дата: 2026-09-10
* Затрагивает: §4.4, §4.5

## Контекст

После `Entry` фокус живёт в контролах, и на Win32 это ломало три вещи сразу:
Tab между контролами не ходил (обычное окно — не диалог), `KeyPressed` окна
видел клавиши только пока фокус был на самом окне, и не было способа
поставить фокус программно. Wine в этой сессии удалось установить, так что
Win32-ветку впервые удалось увидеть и погонять с клавиатуры (xdotool под Xvfb).

## Найдено под Wine, установленные факты

1. **Текст приходил задом наперёд** («novaya» → «ayavon»). Причина
   установлена по коду, не угадана: `QueueUpdate` выполняет обработчик под
   `vreactive.Batch`, поэтому `Text.OnChange` срабатывает после commit'а
   батча — когда флаг `syncing` уже сброшен. Правка с платформы уходила
   обратно в `SetWindowText`, тот ставит каретку в начало, следующий символ
   вставлялся перед предыдущими. На GTK не проявлялось: `gtk_entry_set_text`
   с тем же текстом ничего не делает. У `CheckBox` тот же дефект, но
   безвредный (повторный `BM_SETCHECK` тем же значением).
2. **Порядок Tab = порядок создания** (Z-order). В showcase чекбоксы создаются
   после кнопок (список растёт на лету), и Tab с «Добавить» уходил на «Гнать
   все цели» и «Выход», минуя список; Space на «Выход» закрывал окно —
   первый «чёрный экран» в сессии был именно этим. GTK так не делает:
   `GtkFixed` сортирует цепочку фокуса по координатам.

## Решение

1. **Эхо-защита по значению, а не по времени.** Виджет помнит
   `platformText`/`platformChecked` — что платформа держит (что ей записали
   или что она сообщила). `OnChange` с этим значением — не запись; событие с
   этим значением — не правка (`Changed` больше не стреляет на собственную
   запись программы). Окна для ошибки нет при любом планировании
   уведомлений. Headless теперь, как обе платформы, отвечает событием на
   программную запись — иначе тест этого не видит.
2. **`widget.Focus()`** — `gtk_widget_grab_focus` / `SetFocus`. На Win32 до
   показа окна запрос запоминается и применяется на `WM_SETFOCUS` окна; там же
   окно отдаёт фокус первому tab stop, если никто не просил, а при
   деактивации (`WM_ACTIVATE`) запоминает, у кого он был — то, что обычно
   делает менеджер диалога.
3. **`IsDialogMessageW`** в цикле сообщений: Tab/Shift+Tab/мнемоники. Enter в
   поле снимается раньше него; Enter/Esc вне поля превращаются в `WM_COMMAND`
   с IDOK/IDCANCEL (1/2), под которые нет контролов — проходят мимо.
4. **Порядок Tab на Win32 следует раскладке**: после каждого `ApplyLayout`
   Z-order пересортировывается по верхнему краю, затем по левому — то же
   правило, что у GTK. Проверено под Wine: Tab с поля идёт на «Добавить», затем
   по чекбоксам сверху вниз, Space их переключает.
5. **`KeyPressed` окна видит все клавиши окна**: события снимаются в цикле
   сообщений для любого `hwnd` окна (само окно или его контрол), как
   `key-press-event` toplevel'а в GTK; из `wndProc` эмиссия убрана.

## Проверено

* headless: `Focus`, никакой записи назад при правке с платформы (тест падал
  на старом `api.go`, проходит на новом), `Changed` только на правки.
* GTK под Xvfb: `Focus()` до и после показа (`gtk_widget_is_focus`).
* Win32 под Wine, `backends/win32/win32test` (собирается `GOOS=windows go test
  -c`, запускается `wine`): фокус на поле до показа, `WM_CHAR`×3 → `Changed`
  [a ab abc] в порядке, Enter → `Activated`, Tab → фокус на кнопке. В CI на
  windows-latest тот же тест пропускается, если у раннера нет desktop-сессии.
* Скриншоты showcase под Wine до и после.

## Не сделано

* `Focused`-событие/свойство и `Focus` для окна — не понадобилось.
* Под Wine кнопка «Добавить» отрисовывается впритык к тексту
  (`BCM_GETIDEALSIZE` под Wine, похоже, не добавляет отступов). Что делает
  настоящий Windows — данных нет; проверка ноутбуком.
