# ADR-0004. Showcase проекта crescent и порядок фаз

* Статус: принято
* Дата: 2026-09-08
* Затрагивает: §2.7, §8

## Контекст

§2.7 требует развивать библиотеку через живые showcase. Первой реальной
задачей оказался менеджер фоновых задач Codex — приложение, которое следит
за сессиями `/goal`, ждёт сброса лимита и перезапускает их, живёт в трее и
показывает список целей. Он вынесен в отдельный репозиторий
[crescent](https://github.com/unxed/crescent); здесь остаётся оконная оболочка
как showcase.

Следующий showcase — `imgy`, просмотрщик изображений. Его набор контролов
отличается от crescent: ему нужны область изображения, миниатюры, навигация и
метаданные. Эти части добавляются по мере появления пользовательского
сценария, во всех поддерживаемых бэкендах и через auto layout.

## Решение

1. Showcase crescent остаётся регрессионным примером нативных контролов,
   layout и фоновой логики.
2. `showcase/imgy` развивается отдельными видимыми этапами; новые контролы
   получают реализацию для каждого поддерживаемого бэкенда.
3. Все showcase размещают контролы через общий constraint layout. Нативные
   layout-системы не становятся вторым источником геометрии.

## Последствия

* Библиотека растёт по реальным потребностям двух showcase.
* `Caps.TrayIcon` остаётся capability-флагом общего backend API.
* Новые backend-функции проверяются на доступных платформах в CI.

## Альтернативы

* Писать showcase напрямую на platform API — отвергнуто: так API библиотеки
  перестаёт проверяться реальным приложением.
* Добавлять контролы только в один backend — отвергнуто: showcase теряет
  возможность переключаться между платформами.
